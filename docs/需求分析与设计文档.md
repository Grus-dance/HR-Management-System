## 1. 项目背景与目标

X 公司的人事档案涉及员工一般信息与深度信息（曾就职经历、薪酬、业绩等）的管理。系统需要区分**管理者、一般用户、个人用户**三类角色，做到"各管一段、互不越权"：管理者只看不改、一般用户负责账号与薪酬事务、个人用户只维护自己的档案。

项目目标：

1. 用三层架构实现一个可运行、可演示、职责清晰的 B/S 人事管理系统；
2. 页面简洁清晰，信息分层展示，关键操作路径不超过三步；
3. 完整覆盖题目基础版、指定设计与进阶版的全部要求；
4. 具备基本的认证、授权、输入校验与异常处理能力。

## 2. 需求分析

### 2.1 用户角色

| 角色 | 系统标识 | 典型岗位 | 说明 |
| --- | --- | --- | --- |
| 管理者 | `MANAGER` | 总经理 | 查看全部员工信息（含离职员工）、调整薪酬等级、查看绩效并发私发红包、查看薪资/业绩分析 |
| 一般用户 | `HR` | 人力资源专员/经理 | 新建用户、重置密码、调整津贴与奖金基数、审核业绩 |
| 个人用户 | `EMPLOYEE` | 普通员工 | 维护自己的可编辑信息、提交业绩、查看自己的薪资与红包、下载自己的 PDF 简历 |

三类角色本身也都是员工：管理者与一般用户在员工信息表中同样拥有员工编号，并以个人身份维护自己的信息（题目要求）。因此 `employee` 表存放所有人员，`user_account` 表只负责登录凭据与角色。

| 新建用户（建档 + 账号） | ✘ | ✔ | ✘ |

### 2.4 业务规则

| 编号 | 规则 |
| --- | --- |
| BR-01 | 薪酬构成：`应发 = 基本工资（等级决定） + 岗位津贴 + 绩效奖金 + 红包` |
| BR-02 | 绩效奖金 = `基本工资 × 奖金比例 × 有效业绩分 / 100`；奖金比例默认 0.20，由一般用户调整，取值 0–1 |
| BR-03 | 业绩按月唯一（`employee_id + period` 唯一索引），分值 0–100；仅 `PENDING` 状态可由本人修改/删除 |
| BR-04 | 业绩审核通过后不可撤销；驳回后本人可在同月重新提交（覆盖为新的 `PENDING`） |
| BR-05 | 红包金额 > 0，单笔上限 50,000 元；发放人必须是管理者；红包归属月份按发放时间所在自然月计 |
| BR-06 | 薪酬等级调整与津贴调整必须填写原因（2–200 字），写入 `salary_adjustment` 流水 |
| BR-07 | 离职：`status` 由 `ACTIVE` 改为 `RESIGNED` 并写 `resign_date`；账号 `status` 同步失效；登录时统一提示"账号或密码错误" |
| BR-08 | 锁定字段：姓名、性别、出生日期、身份证号、部门、职位、入职日期、薪酬等级、学历、毕业院校、专业。创建后任何角色均不可通过个人信息接口修改（如需更正由管理员在数据库层处理，系统不提供入口） |
| BR-09 | 员工编号全局唯一，格式 `[A-Z]\d{4}`（如 `X1001`），创建时校验 |
| BR-10 | 身份证号在接口输出中脱敏（保留前 4 位与后 4 位） |
| BR-11 | 所有列表接口分页，默认每页 10 条；金额保留 2 位小数，比率保留 4 位小数 |
| BR-12 | 时间统一使用 `Asia/Shanghai`，月份格式 `yyyy-MM` |

### 2.5 数据可见性

- 个人用户：仅本人档案、本人薪资、本人业绩、本人红包、本人简历。
- 一般用户：在职员工档案与薪酬（用于调整与审核），不可见离职员工；不可见他人红包附言。
- 管理者：全部员工（含离职）档案、薪酬、业绩、红包；**不可查看他人简历**，本人简历可在「我的信息」下载（一般用户与个人用户同理）。

### 2.7 假设、约束与待确认

1. **JDK 版本**：题目写 JDK 24，本机仅安装 JDK 25，经确认使用 JDK 25 编译运行，`pom.xml` 中 `java.version=25`。
2. **数据库**：使用本机 MySQL 8.0.19（3306），库名 `hrm`，字符集 `utf8mb4`；需要 root 密码（待提供）。

4. **离线演示**：ECharts 静态文件随项目打包，不依赖 CDN。
5. **演示数据**：预置 15 名员工（1 管理者、2 一般用户、12 个人用户，其中 1 人离职）、6 个月薪资与业绩历史；统一初始密码 123456。
6. 不涉及真实个人信息，全部为虚构数据。

## 3. 总体设计

### 3.1 技术选型

| 层次 | 技术 | 版本 | 选型理由 |
| --- | --- | --- | --- |
| 运行环境 | OpenJDK (Temurin) | 25 | 本机可用，满足 JDK 24+ 要求 |
| 框架 | Spring Boot | 4.0.9 | 自动配置、内嵌 Tomcat、REST 支持 |
| Web | Spring MVC | 随 Boot | `@RestController` + 静态资源 |
| 持久层 | MyBatis | 4.0.1 | SQL 可控、XML 动态 SQL、贴合课程"数据访问层"教学 |
| 数据库 | MySQL | 8.0.19 | 本机已运行，支持事务与唯一约束 |
| 连接池 | HikariCP | 随 Boot | 默认、稳定 |
| 校验 | Jakarta Validation | 随 Boot | DTO 声明式校验 |
| PDF | Apache PDFBox | 3.0.x | 纯 Java 生成 PDF，支持嵌入中文字体 |
| 前端 | HTML5 / CSS3 / ES6 | — | 无构建链，直接由 Spring Boot 托管 |
| 图表 | ECharts | 5.x（本地文件） | 折线/饼图开箱即用，中文友好 |
| 密码 | PBKDF2-HMAC-SHA256 | JDK 内置 | 不引入额外安全框架，迭代 12 万次 + 随机盐 |
| 构建 | Maven | 3.9（IDEA 内置） | 依赖管理与打包 |

### 3.2 三层架构与依赖方向

```
┌──────────────────────────────────────────────────────────────┐
│  表现层 web（Controller / DTO / VO / Interceptor / Advice）   │
│  职责：HTTP 协议、参数校验、会话与角色、响应封装、异常转译        │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只依赖 Service 接口
┌───────────────────────────▼──────────────────────────────────┐
│  业务逻辑层 service（接口 + impl）                            │
│  职责：业务规则、事务边界、权限归属校验、实体→VO 装配            │
│  不依赖 Servlet API，便于单元测试                              │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只依赖 Mapper 接口与实体
┌───────────────────────────▼──────────────────────────────────┐
│  数据访问层 mapper（MyBatis 接口 + XML） + entity              │
│  职责：SQL、结果映射、分页与动态条件                            │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
                        MySQL 8 (hrm)
```

分层约束（评审时可逐条对照）：

1. Controller 不注入 Mapper，Service 不注入 Controller；不存在反向依赖。
2. Controller 不直接返回实体，统一返回 VO；入参使用 DTO 并带校验注解。
3. Service 接口暴露业务能力，实现类 `@Transactional` 控制事务；跨表写操作（建档 + 建号、调整 + 流水）在同一事务内。
4. Mapper 只做数据存取，不含业务判断；动态 SQL 全部使用 `#{}` 参数绑定。
5. 横切关注点集中在 `common` / `config`：统一响应、全局异常、登录拦截、密码哈希。

## 4. 数据库设计

### 4.1 实体关系

```
salary_grade 1 ─── n employee 1 ─── 1 user_account
                     │  1
                     ├── 1 employee_salary
                     ├── n work_experience
                     ├── n performance_record
                     ├── n red_packet
                     ├── n salary_monthly
                     └── n salary_adjustment
```

### 4.2 表清单

| 表名 | 说明 |
| --- | --- |
| `salary_grade` | 薪酬等级字典（等级 → 基本工资） |
| `employee` | 员工档案（一般信息 + 教育 + 在职状态） |
| `user_account` | 登录账号、密码哈希、角色、首次改密标记 |
| `employee_salary` | 员工薪酬参数（岗位津贴、绩效奖金比例） |
| `work_experience` | 曾就职经历（深度信息） |
| `performance_record` | 业绩记录（含审核状态） |
| `red_packet` | 私发红包 |
| `salary_monthly` | 月度薪资快照（历史曲线数据源） |
| `salary_adjustment` | 薪酬调整流水（审计） |

### 4.3 表结构

#### salary_grade

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| grade_code | VARCHAR(8) | PK | 等级编码 G1–G8 |
| grade_name | VARCHAR(40) | NOT NULL | 等级名称 |
| base_salary | DECIMAL(12,2) | NOT NULL | 基本工资 |
| description | VARCHAR(200) |  | 说明 |

### 4.4 关键设计说明

1. **锁定字段的落地方式**：`EmployeeMapper.updateProfile` 的 SQL 只包含可编辑列（phone/email/address/emergency_*），即使前端伪造 JSON 传入 `name`，也无法写入；这是"不可修改"的实现级保证。
2. **离职的落地方式**：`employee.status` + `user_account` 关联校验，登录时 `status != ACTIVE` 直接拒绝；HR 列表固定 `status='ACTIVE'`，管理者列表可切换"全部/在职/离职"。
3. **月度薪资**：`salary_monthly` 只存历史快照；当月实时计算，保证调整等级/津贴后当月金额立即变化，历史月份保持不变。
4. **审计**：等级与津贴调整写 `salary_adjustment`；业绩审核人/时间落 `performance_record`；红包发放人/时间落 `red_packet`。
5. **唯一约束**：员工编号、一人一账号、一人一月一条业绩、一人一月一条薪资快照，均由数据库唯一索引兜底，业务层重复时返回 409。

## 6. 关键流程

### 6.1 登录与首次改密

```
用户输入工号/密码
   → AuthService.login
       → 按工号查员工 + 账号
       → 员工不存在 / 已离职 / 账号不存在 → 统一“工号或密码错误”
       → PasswordHasher.verify
       → 失败计数?（本期不做锁定）→ 400
       → 写 Session(LOGIN_USER)，更新 last_login_at
   → 返回角色与 mustChangePassword
   → 前端：mustChangePassword=true 时强制跳转改密弹窗，改密成功前不渲染业务页
```

### 6.2 一般用户新建用户

```
填写档案（工号/姓名/性别/部门/职位/等级/入职日期/学历/联系方式）
   → 校验工号格式与唯一性（409）
   → @Transactional：
        insert employee
        insert employee_salary（默认津贴 0、比例 0.2）
        insert user_account（role=EMPLOYEE，hash("123456")，must_change=1）
   → 返回员工 id 与初始密码提示
```

### 6.3 业绩提交 → 确认 → 计薪

```
个人用户提交（月份、分值、自评） → status=PENDING
一般用户审核：
   通过 → status=APPROVED，记录审核人与时间
   驳回 → status=REJECTED + 意见；本人可重新提交（同月覆盖）
计薪：应发 = 基本工资 + 津贴 + 基本工资×比例×有效分/100 + 当月红包
```

### 6.4 管理者薪酬等级调整（指定设计）

```
薪酬等级调整页
   ├─ 默认行：工号 | 姓名 | 部门 | 当前等级 | 基本工资 | 本月绩效 | [展开] 
   └─ 点击“展开”
        → GET /api/mgr/employees/{id}（按需加载）
        → 在行下方插入详情行（colspan=7）：津贴、奖金比例、近 3 月绩效、
          曾就职、最近调整记录、等级选择 + 原因 + [保存调整]
        → 按钮文案“收起”，图标旋转 180°，aria-expanded=true
        → 点击“收起”移除详情行（或隐藏），按钮复原
   保存 → PUT /api/mgr/employees/{id}/grade → 刷新行数据与统计卡片
```

### 6.5 私发红包

```
管理者在“绩效与红包”页选择员工（可带当月绩效上下文）
   → 输入金额、附言 → POST /api/mgr/red-packets
   → 校验：仅 MANAGER；金额 (0, 50000]；员工存在且在职
   → insert red_packet（sender_id=当前管理者）
   → 当月薪资实时计算时计入；员工“我的红包”可见附言
```

### 6.6 PDF 简历

```
员工点击“下载简历”
   → GET /api/me/resume.pdf
   → ResumeService：查本人档案 + 曾就职 + 教育
   → PDFBox 渲染：标题、基本信息、教育背景、工作经历、在职信息
   → 字体：系统黑体优先，回退其他中文字体；无字体 → 500 + 明确提示
   → 响应 Content-Disposition: attachment; filename="resume_X1001_陈晨.pdf"
```

### 6.7 数据分析

```
管理者勾选员工（默认前 5 名在职员工）→ GET /api/mgr/analytics
   → 薪资比例：各员工当月应发 / 合计（饼图）
   → 薪资曲线：近 6 个月，每人一条（历史取 salary_monthly，当月实时计算）
   → 业绩曲线：近 6 个月有效业绩分，每人一条（无数据补 null）
```

### 7.4 指定设计：薪酬页"展开"交互

- 触发元素：每行右侧「展开 ▾」按钮（`button.btn-ghost`，带 `aria-expanded`、`aria-controls`）。
- 默认态：仅常用列可见；详情行不存在于 DOM（懒加载），减少首屏请求与信息噪音。
- 展开态：在目标行下方插入 `<tr class="detail-row"><td colspan="7">`，内部为两栏卡片：
  - 左：津贴、奖金比例、近 3 月绩效（小表格）、曾就职经历；
  - 右：等级选择、调整原因、保存按钮、最近 3 条调整流水。
- 收起：移除详情行，按钮文案与图标复位；同一时间只允许展开一行（互斥），避免页面过长。
- 可访问性：按钮 `aria-expanded` 同步；`Esc` 收起；展开后焦点移至详情区首个可交互元素。

### 7.5 顶部工作台与个人信息弹窗

- 顶部导航固定高度 64px：左侧品牌，中间按角色渲染工作台菜单（选中项为粉色胶囊），右侧为个人信息（头像 + 姓名 + 角色/工号）。
- 点击右上角个人信息弹出「账号信息」弹窗，弹窗内提供「修改密码」与「退出登录」，不再占用页面空间。
- 修改密码为二级弹窗，调用 `PUT /api/auth/password`；成功后提示并关闭弹窗，首次改密场景直接回到角色首页。退出调用 `POST /api/auth/logout`，确认后回到登录页。
- 后端接口契约不变：`/api/auth/me` 提供姓名、角色、工号与首次改密标记；页面拦截器仍按 `/manager/**`、`/hr/**`、`/me/**` 校验角色，本次仅调整前端布局与交互，无需新增接口。

## 8. 安全设计

| 风险 | 措施 |
| --- | --- |
| 密码泄露 | PBKDF2-HMAC-SHA256，12 万次迭代，16 字节随机盐，常量时间比较；数据库中不存明文 |
| 会话劫持 | 登录后重建 Session；Cookie `HttpOnly`、`SameSite=Lax`；超时 30 分钟；退出即失效 |
| 越权访问 | URL 前缀角色拦截 + 业务层归属校验（`employeeId == session.employeeId`）；管理者/HR 接口分离 |
| SQL 注入 | MyBatis 全部 `#{}` 预编译；排序字段白名单 |
| XSS | 前端统一 `textContent` 写入，必要时 `escapeHtml`；不使用 `innerHTML` 拼接用户输入 |
| 敏感信息 | 身份证脱敏输出；简历仅本人可下载；红包附言仅收件人可见；错误提示不区分"账号不存在/密码错误" |
| 参数篡改 | 锁定字段不出现在更新 SQL；金额、比率服务端校验；分页大小上限 100 |
| 重复提交 | 唯一索引 + 业务层 409；审核只允许 `PENDING → APPROVED/REJECTED` |

---

## 9. 异常处理与日志

- `BusinessException(code, message)` 由 `GlobalExceptionHandler` 转成统一响应；未知异常记录 ERROR 日志并返回 50001，不向前端暴露堆栈。
- 参数校验失败聚合 `MethodArgumentNotValidException` 的字段错误，返回首条可读提示。
- 登录失败、权限拒绝、关键写操作（建号、调整、审核、红包）记录 INFO 日志（含操作人、目标、结果）。
- 前端 `api.js` 统一处理 401（跳登录）、403（提示无权限）、409/400（Toast 提示）。
